# Project
A WXT MV3 Chrome extension that guarantees a searched city in Clalit's "Tamuz" / Clalit Smile hygienist (שיננית) booking flow shows ONLY that city and ALL of its branches - when the user asked for that city's clinics; an explicit "מרפאות מכל הארץ" search is passed through untouched - and that every row's distance is measured from where the user actually is. Content scripts do all the work; no storage, and the only permissions are `geolocation` + `offscreen` - the position is the EXTENSION's own reading, never the site's (see Architecture).
- The booking UI is an iframe on `e-services.clalit.co.il` (behind login); `clalitsmile.co.il` is only the marketing site. Full teardown in `docs/reverse-engineering.md` - read it before touching the interceptor, `smile.ts` or `targets.ts`.
- Mechanism: patch `fetch`/`XMLHttpRequest` in the page's MAIN world (`document_start`, all frames) and rewrite the server responses - which are a JSON envelope `{ data }` wrapping a SERVER-RENDERED HTML fragment (`li.diary` rows), not JSON data.

# Stack
- pnpm
- WXT extension framework, TypeScript content scripts; our own DOM is Svelte 5 (runes) mounted in a WXT shadow-root UI (`createShadowRootUi`; component CSS compiled in via `css: "injected"` so re-injected dev generations need no browser.* APIs) - never hand-rolled
- TypeScript (100% type safety, let TypeScript infer return types - never write them explicitly)
- zod for every external input (`src/lib/schemas.ts`)
- @webext-core/messaging - the window channel (`/page`, `src/lib/messaging-page.ts`) for bridge ⇄ MAIN, and the runtime channel (`src/lib/messaging-runtime.ts`) for bridge ⇄ background ⇄ offscreen, which exists only to carry the user's position
- oxlint (type-aware, logic rules) + ESLint (stylistic + local rules); dev tooling runs via tsx (Node, never Bun - web-ext-run depends on Node's child_process socket handling)

# Architecture
Three content scripts, all `allFrames` (the booking UI is an iframe):
- `src/entrypoints/clalit-interceptor.content.ts` - MAIN world: patches fetch/XHR, rewrites the outgoing search (area → all-country, `sortValue=4` → `3`), filters responses to the city, aggregates the remaining server pages, appends no-diary branches, re-ranks by live location, mints a synthetic row's diary GUID at click time (one fresh search in the SEARCHED service → navigate to that clinic's page; on miss restore the user's search session + heal the rendered links), re-drives the search on the server-rendered "back" restore document (`isRestoreSearch=True`, which bypasses the patches - docs §6d), and opens the site's clinic-details lightbox for no-GUID branches (fragment recomposed from the committed directory, shown via the page's own `z.showDialog`)
- `src/entrypoints/clalit-bridge.content.ts` - ISOLATED world: reads the city from the site's search box, pushes config to MAIN over the window channel, renders the status badge (top frame only; child frames relay state up via `postMessage`), and answers MAIN's position request by asking the background

Plus the two contexts that exist for ONE thing - reading the position under the extension's own permission instead of the site's (a content script's `navigator.geolocation` is the PAGE's, and is empty whenever the user refused Clalit):
- `src/entrypoints/background.ts` - opens an offscreen document per read, waits for its report, closes it again; concurrent askers (one bridge per frame) share the single in-flight read
- `src/entrypoints/offscreen/` - the ONLY call to `navigator.geolocation` in the codebase. It reads on load and REPORTS to the background (never waits to be asked, so it cannot be messaged before its listeners are up)

Key lib modules - the interceptor owns only the patches and the wiring, each behaviour lives in its own module:
- `targets.ts` - SSOT for hosts, matches/`host_permissions`, search-box selectors, guarantee mode, Smile endpoint paths, endpoint rules. Imported by both runtime and `wxt.config.ts`
- `smile.ts` - the HTML-fragment guarantee (pure string→string); `transform.ts` - the generic JSON guarantee (heuristic/rule-based)
- `smile-session.ts` - the ONE shared Smile server session: what the last search was, which services still answer, and every `/Zimunet/SmileClinic` call, made with the page's credentials and its UNPATCHED fetch. The modules below read and write this object instead of keeping their own copy
- `smile-aggregation.ts` - city completeness after the first render: fetch the remaining server pages, dedup by clinic name, append the branches Tamuz omits from the committed directory, then re-rank
- `live-distance.ts` - every row's distance from the live position, and the re-rank when the home-distance sort is active (stable; unknown-coordinate rows keep server order at the end). It never reads a position itself - `page-position.ts` asks the bridge, and one fix serves the whole list (`POSITION_MAX_AGE_MS` in `geo.ts` is the one home for that window)
- `smile-clinic-page.ts` - the appointments page for a branch Tamuz has no handle for: a REAL row's slots page, borrowed via a `#clalit-city-clinic=` hash, retitled to the branch and answered with the site's OWN empty-month payload so nothing of the lender's is left to book (docs §12i)
- `smile-availability.ts` - whether an appended branch can be booked FOR THE SEARCHED SERVICE: one sweep per rendered list (`session.sweepListedBranches`) re-asks that one service, and its search STAYS the session's - every displayed real row is healed onto its GUIDs and every branch it lists gives up the slots link its row carried, so a click needs no round trip (docs §12l). Keeps the soonest slot the listing row printed, paints a red button + reason on the rest, verdicts cached 5 min
- `smile-row-actions.ts` - a synthetic row's two buttons: "לכל התורים" opens a page of THAT clinic in THAT service or nothing - the sweep's own link if it found one (the row is then a plain `data-action-link` the SITE opens), else the borrowed page tailored to the branch, else the old click-time mint when no verdict is fresh, else stay put and repaint the row; "מידע נוסף" composes the site's own lightbox from a real row of the current search
- `site-chrome.ts` - the PAGE's own chrome reused instead of ours: `window.z` loader/lightbox plus the DOM waits. MAIN-world only, every call cosmetic
- `schemas.ts` - zod schemas for every external input (call `schema.safeParse()` at the boundary); `messaging.ts` - the contracts for BOTH channels, `messaging-page.ts` (window) + `messaging-runtime.ts` (runtime); `page-position.ts` - the MAIN world's only way to a position; `text.ts` (`normalizeCity`) + `html.ts` (`escapeHtml`) - the shared string helpers
- `clinic-coord-fixes.ts` - the few Clalit coordinates that contradict their own address (sourced, one per entry); every distance path reads `clinicCoords(navCode)`, never the generated map directly
- `geo.ts` (haversine) + `clinic-directory.ts` - GENERATED from Clalit's public `nearme.clalit.co.il/c.json` by `pnpm clinics:fetch`; never hand-edit (ESLint ignores it). `clinics.ts` is a different code space (marketing-site 9xxx codes), reference only
- `phone-links.ts` + `PhoneLinks.svelte` - phone presentation in one home: `formatPhone` (the directory's digits → what the site prints) and the markup, a Svelte component so the whitespace between two numbers is visible in a template instead of buried in appendChild calls. Mounted into a row's telephone slot, the composed lightbox and the message box alike - the last two read the slot's HTML immediately (hence `flushSync`) and the lightbox's slot belongs to a DOMParser document (hence the import)
- `status-badge.svelte.ts` + `StatusBadge.svelte` - pure UI

# Engineering conventions
- SSOT / DRY - every fact has one authoritative home and everything else reads from it: hosts/selectors/endpoints live only in `targets.ts`, message shapes only in `messaging.ts` + `schemas.ts`, coordinates only in `clinic-directory.ts`. Never re-derive or duplicate a value another module already owns
- MAIN vs ISOLATED split is load-bearing: the MAIN world can patch the page's `fetch`/XHR but has NO `browser.*` access; the ISOLATED world has extension APIs but cannot patch page globals. They talk only over the window channel. Anything imported by the interceptor must stay free of extension APIs and dependency-light
- The city comes from the SITE'S SEARCH BOX (and the submitted search request body), never from storage or config. There is nothing to configure and nothing persisted; the on/off toggle is session-only
- The guarantee applies to ONE of the form's two radios. "מרפאות מאזור היישוב" (`IsShowClinicsFromAreaCity=1`) is the search it exists for - rewritten to all-country, filtered to the city, completed with the city's missing branches. "מרפאות מכל הארץ" (`=0`) is a request for the whole country: every response of such a search passes through untouched (no filter, no appended rows, no aggregation, no re-rank), because narrowing it would answer a question the user did not ask
- A row answers for the SERVICE THE USER SEARCHED, never another one. A Smile slots page belongs to a (clinic, service) pair and says so in its own header - "תור לשיננות" vs "תור לבדיקת רופא שיניים" - so a diary minted under a different specialization opens a different appointment than the row promised. Same rule for the date: an appended row prints a soonest slot only when that service has one
- Transforms are order-preserving for the SERVER's rows: it already sorted them by the user's chosen distance-vs-time option, so filter without re-sorting. Two deliberate exceptions, both about rows the sort cannot read: the live-location re-rank when the home-distance sort is active (stable, unknown-coordinate rows keep server order at the end), and the appended block's own order - a branch with no diary has no soonest appointment, so it is ordered bookable-first then nearest-first instead of by clinic code
- zod at every trust boundary: window-channel payloads (the frame-relay ones cross frames, so any page script could forge them) and the network envelope all go through `schemas.ts` at the edge; parse with `schema.safeParse()` and ignore a malformed value (`{ success: false }`), never throw on it. Inner code works only with validated shapes
- Message passing goes through **@webext-core/messaging**: window messaging (`/page`, `messaging-page.ts`) for bridge ⇄ MAIN, runtime messaging (`messaging-runtime.ts`) for bridge ⇄ background ⇄ offscreen, both with contracts in `messaging.ts` - never hand-roll `browser.runtime` or ad-hoc `postMessage` for them. The cross-FRAME relay (child iframe → top frame's badge, and the toggle back) rides the SAME window channel: its `sendMessage` takes the window to post into, so `sendPageMessage(type, data, "*", window.top)` addresses another frame with the protocol rather than around it. Those messages are one-way (a reply cannot cross frames), so nothing awaits them, and they are zod-validated on receipt like every other boundary. There is no ad-hoc channel left in the codebase - do not introduce one
- No permission creep: `geolocation` + `offscreen` and nothing else, no storage, and `host_permissions` is derived from `CONTENT_MATCHES` so access can never drift. Both permissions serve the same single feature and are spent in one place (the offscreen document); a new permission needs the same standard. Ranking still works off the COMMITTED directory - zero runtime network beyond the page's own session calls
- Gate: `pnpm lint` AND `pnpm typecheck` must both pass after every change. `pnpm lint` runs oxlint --fix (relaxed `.oxlintrc.fix.json`) → eslint --fix (strips dead imports) → plain oxlint as the final check

# Code style
- Function declarations, not arrow-consts (`func-style`); early returns; `for-of` over `.forEach`
- Prefer destructuring for variables that point to object props when it improves readability - `const { city, street } = branch` over repeated `branch.city` / `branch.street`, `({ data }) => …` over `msg => msg.data`, and `const { ownerDocument } = container` over `const doc = container.ownerDocument` (prefer the prop's own name to an invented alias when the name is clear). Judgment call, not mechanical: a truly single-use prop read once stays as-is; reach for it when the value is used more than once or destructuring names it more clearly
- No comments unless necessary - descriptive names first; no em dashes, use hyphens
- No type assertions (`consistent-type-assertions: never`), no `any`, no `@ts-` comments
- Content-script code never reads `process` - Node globals exist only in `scripts/` and config files
- Minimize indentation: avoid nested `try`/`catch` - flatten with early returns, `.catch()` on the awaited promise, or an extracted function. One `try` per function is the ceiling
- `await`, never `.then` - an async function with `await` reads top to bottom, and a floating chain hides where the work continues. `.catch()` on the awaited promise stays: it is how a failure is swallowed without a `try` block
- NEVER `setTimeout` / `setInterval` - not for polling, not for debouncing, not as a deadline. Wait on the thing itself: a `MutationObserver` for DOM the site renders, the page's own events (`load`, `DOMContentLoaded`), or the API's own timeout option (`getCurrentPosition`'s). A timer is a guess about someone else's timing, and it is wrong on a slow machine and wasteful on a fast one
- Extract an `if`/ternary/guard condition into a descriptive `is`-prefixed boolean rather than inlining the raw expression - the named boolean reads as the documentation
- `.replaceAll` for every global replace - `.replace(/…/g)` says the same thing in a way that reads like a single replacement. A non-global `.replace(/…/)` stays as it is
- An event handler's parameter type is INFERRED, never written - `ctx.addEventListener(document, "click", e => …)`, not `(e: MouseEvent)`. The listener's own signature already says what the event is, and repeating it is a second copy that can drift from the first. Same rule wherever a callback's parameter type comes from the API it is passed to (`onPageMessage`, `MutationObserver`, `watcher.on`). Only write the type when TypeScript would otherwise infer `any`

# Naming conventions
Shared with `avi/youtube-time-manager` - the same conventions apply across Avi's extensions.
- Variables and functions: `camelCase`, full words (no abbreviations - `specialization`, not `spec`)
- Module-level constants: `SCREAMING_SNAKE_CASE`; a closed set of strings is an enum or `as const`
- Element variables: `el` prefix (`elRow`, `elDialog`, `elLoader`)
- Index variables: `i` prefix (`iRow`), or bare `i` when iterating in a `for` loop / higher-order function
- Booleans: `is` prefix, phrased positively (`isEnabled`, never `isDisabled`/`isNotEnabled`)
- Event-handler first parameter is always `e`
- `safeParse` results: collapse to a boolean when only validity matters (`schema.safeParse(x).success`), otherwise store as `parsed` - never `result` or `<x>Parse`

# Dev workflow
`pnpm ext:dev` (tsx `scripts/dev.ts`) is the whole loop:
- Builds the dev bundle (inline source maps), clones your real Chrome profile into `user-profiles/chrome` (carries your Clalit login, fully decoupled from the real session), launches Chrome via web-ext-run with a FIXED CDP port `9223` (`CDP_PORT` in `scripts/dev-chrome.ts`; `.mcp.json` mirrors it manually - update both if it ever changes). chrome-devtools-mcp attaches with `--browser-url http://127.0.0.1:9223`
- On a `src/` change it rebuilds and EVALUATES the fresh bundles into every Clalit frame over CDP - interceptor into MAIN, bridge into the EXTENSION's isolated world (matched by execution-context name = the built manifest's `name`, newest context per frame) - it does NOT reload the tab, because a reload resets the Tamuz booking SPA to its home screen and loses the search state. The extension is NOT reloaded either, and that is what keeps this working: an extension reload REVOKES every open tab's isolated world (`browser.runtime.id` gone, "Extension context invalidated"), so the bridge could no longer reach the background and the position would silently answer `null`. The dev loop needs no permission of its own for any of this
- A reload is reserved for what Chrome caches and only a reload refreshes - `manifest.json`, `background.js`, `offscreen.html` (hashed after every build, `reloadFingerprint`) - and it costs the open tabs, which are reloaded with it
- Chrome keeps serving its CACHED copy of the content scripts to any page loaded after that, so every tab is stamped with the build it runs (`__clalitCityDevBuild`) and a 3 s reconcile injects the current build into any tab that is behind - a tab you reload yourself is current again within a tick
- Standing the previous generation down is WXT's own `ContentScriptContext`, not code of ours: constructing it announces this script and ABORTS the older context of the same name. So everything a content script installs hangs on that ctx - listeners via `ctx.addEventListener`, the badge via `createShadowRootUi` - and the interceptor additionally restores `fetch`/XHR in `ctx.onInvalidated`, since page globals are the one thing the framework cannot put back. A MAIN-world script gets no ctx from WXT (its `isValid` reads `browser.runtime`), so the interceptor constructs one itself and uses `ctx.signal`
- Changes under `scripts/` need `pnpm ext:dev` restarted - tsx loaded them at startup, and only `src/`, `wxt.config.ts` and the env files are watched
- `wxt.config.ts` / `.env` changes DO reload the open tabs (they reshape the manifest); a manifest change may still need a manual reload from `chrome://extensions`
- Dev logs: `.dev-logs/dev.log`. Dev builds also log interesting requests to the PAGE console (`[clalit-city] …`) - that is the discovery mode for filling in `ENDPOINT_RULES`
- `pnpm ext:build` / `pnpm ext:zip` for production (no source maps); `pnpm clinics:fetch` regenerates `clinic-directory.ts` when Clalit opens/moves clinics
- If `ext:dev` dies at launch with `CDP connection closed before response to Extensions.loadUnpacked`, a dev Chrome from an earlier session still holds port 9223 - kill ONLY the `chrome.exe` tree whose `--user-data-dir` is `user-profiles\chrome` (inspect command lines first; NEVER a blanket kill on `chrome.exe` - the real Chrome may be running), then relaunch (a leftover instance also means its login is stale; verify with the passive auth probe in docs §5a before assuming it is worth keeping)

Whenever you reverse-engineer ANYTHING about Clalit's systems - an API endpoint, a request/response shape, a data set, a site behavior, an auth quirk - you MUST record both the findings and the method in `docs/reverse-engineering.md` in the same change. Update the existing sections when a shape changes; add a dated section for new discoveries. Read that doc BEFORE probing - most questions are already answered there.

# Gotchas
- The Smile result set is SERVER-SESSION state: sort and `Paging` operate on the session's last search, and each row's diary GUID is valid only for that search. Never splice rows from a second search into the list - that's why the guarantee rewrites the ONE outgoing search to all-country and then filters/aggregates its own responses. Dedup rows by clinic name, not GUID
- The "area" search (`IsShowClinicsFromAreaCity=1`) is a SUBSET that can miss the city's own clinics, and Tamuz omits branches with no bookable diary entirely - hence the all-country rewrite plus synthetic rows from `SMILE_BRANCHES`
- XHR patching subtleties (see interceptor comments before touching): response getters are defined per-instance from `send()`, not `open()`, so stacked dev generations don't clobber the active one; `responseText` throws for `responseType: "json"` - read `response` instead
- When rebuilding a transformed `fetch` Response, drop `content-encoding`/`content-length` - the body is already-decoded JSON and stale headers corrupt the page's read
- City matching is Hebrew-tolerant via `normalizeCity` (geresh/quote/whitespace normalization) with bidirectional substring match - reuse it, don't compare raw strings
